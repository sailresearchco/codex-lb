The parent process account is a soft cache-locality preference, not proof that an independent child owns any upstream state. A regular collaboration child identifies itself with `x-openai-subagent: collab_spawn`, a nonblank `thread-id`, and a different nonblank `x-codex-parent-thread-id`. HTTP compatibility headers and Responses `client_metadata` carry the same signals, with body metadata authoritative.

Those markers establish the scope of the optimization, not portability. The unchanged account-neutral fresh-replay classifier must also accept the canonical request. Opaque agent messages, encrypted history, files, previous responses, conversations, and unknown account-state shapes do not gain independent placement. Exact turn-state, raw legacy ownership, and resolved bridge/file/response ownership still take precedence.

An eligible child omits only the process seed lookup and initialization. Existing child affinity is still consulted and retained. For example, with the process seed on exhausted A and included allowance on B, a fresh account-neutral child may select B; a later request for that child retains B, while the parent and siblings keep their own mappings. A fresh child with nonportable inherited history continues to use the existing process preference. This is a bounded correction to initial placement, not a global fairness controller.

The initiating process preference is traced by git blame to upstream commit `35bbb006b` (PR #1703). The subscription-first change deliberately left initial preferences intact. Client marker provenance is supported by `openai/codex` commit `16e27626e654b29cc2ea696a545b2cd5f29db136`, `responses_metadata.rs` and `turn_metadata.rs`; it does not establish the installed desktop build's exact wire behavior.
